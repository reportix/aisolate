# AIsolate 0.1.20

The first release with the CLI installers attached, and the one that brings airlock versions: an airlock now runs as one or more versions, each with its own pod pair and endpoint.

## Highlights

- **Airlock versions.** An airlock is the container: its space, its name, who may ask it, its models and data sources. A version is what runs: the stages, the model and its prompt, the tools and the code. Several versions of one airlock run side by side, each on `POST /v1/spaces/<space>/airlocks/<airlock>/versions/<version>/chat`. The UI lists an airlock's versions with each one's graph, details and tools; the chat picks one; every audit line, trace and metric names the version that answered. A project deploys one version at a time (`version: v1` in the template), and the same deploy updates it or adds another.
- **The CLI, downloadable.** A signed installer for Windows and an archive for Linux are built on every release and attached below; the macOS package is attached by a maintainer. `aisolate create`, `login`, `build` and `deploy` turn a project into a running airlock.
- **A reset that leaves nothing behind.** Deleting every space also drops the audit trail and the product's Prometheus series, so a demo install starts over clean.
- **Help in the UI.** A Help menu at the foot of the rail links the documentation and the source; the footer and the Settings page are gone.

## Downloads

| File | What it is |
|---|---|
| `aisolate-cli-installer.exe` | The Windows installer, signed; installs for your user and adds the folder to `Path` |
| `aisolate-cli-linux-x64.tar.gz` | The Linux archive: the `aisolate` binary and the licence; unpack and put it on your `PATH` |
| `aisolate-cli-installer.pkg` | The macOS package, installs `/usr/local/bin/aisolate` |
| `SHA256SUMS`, `*.sha256` | Checksums of the files above |

Then check: `aisolate --version`.

## Images

`docker-public.sonatype.reportix.com/aisolate/<app>:0.1.20` for `backend`, `controller`, `airlock`, `airlock-python`, `tool-server`, `tool-server-python` and `keycloak`.

## Upgrading

- The backend's migration turns every deployed airlock into its version `v1`; its pods are replaced once by `<space>-<airlock>-v1-*`, a short outage per airlock.
- The chart release that goes with this one carries the `airlockversions` CRD and the controller's rights to it; upgrade the chart with the images.
- Chat endpoints now name the version. The n8n node and the KNIME extension of the integrations release that goes with this one ask a version; older workflows keep the airlock's endpoint and need the version in the path.
- A project must name its version to update it: a template of the previous release deploys as `v1`.
